## Part 1 — The refactor worklist

Ordered by dependency, not by size. Everything here is work on code that already exists and already
ships. Each item says what "done" means so it can be checked rather than declared.

### Group A — Correctness (do first; cheap, and each one is a real hole)

**A1. Close the two freshness holes.**
`guards/check_derived_fresh.py::DERIVED_GLOBS` omits the two biggest artifacts the gate itself
writes — `web/public/data/sibc_l1_annotations.json` and `web/public/data/atm_pos_insights.json` —
plus `atm_pos_signals.json`. These are committed derived files with no staleness guard, which is the
exact class of bug that produced the "FY26 acceleration jumped to 7.1pp" incident.
*Done when:* all three are in `DERIVED_GLOBS`, the pre-commit hook catches a deliberately stale copy,
and both gates stay green.

**A2. Fix `csv_streak`'s split personality.**
One registry method name resolves to two implementations that are **14% similar** —
`signals/compute/sibc.py` and `signals/compute/atm_pos.py` mean different things by the same spec.
A registry method whose semantics depend on the pipeline is a latent correctness bug, not a style
issue.
*Done when:* either one shared implementation, or two honestly-named methods, with the registry
updated and freshness green across all periods on both pipelines.

**A3. Correct the 34 mislabelled signals.**
34 SIBC Layer-2 signals carry `retire_period` and `migrated_to` but report `current_status:
"pending"` — the string `"retired"` appears zero times in `registry.json` even though
`validate_signal_history.VALID_STATUSES` accepts it. The registry currently claims 38 pending
signals when only 4 genuinely await compute.
*Done when:* status reads `retired`, Check 2e green, and the counts in any doc that quotes them match.

**A4. Declare Python dependencies.**
There is no `requirements.txt`, `pyproject.toml`, `setup.py` or lockfile anywhere — the environment
is entirely implicit. This is invisible until someone else (or a future you) runs the gate on a
clean machine.
*Done when:* a pinned dependency file exists and a fresh-env install runs both gates green.

### Group B — The structural fix (the big one)

**B1. Generalise the payments insight generator.**
`pipelines/atm_pos/generate_atm_pos_insights.py` is 2,086 lines built as ~30 hand-written functions,
one per card, with **zero direct tests**. SIBC's equivalent is 502 lines and registry-driven —
adding a SIBC card is a registry entry; adding a payments card is a new Python function.

The migration path already exists inside the same file: its newer layers (`EVAL_ANCHOR` LLM
representation, `relational_cards`, `pair_cards`, `_dominance_caveat`) are generic and shared with
SIBC. The work is moving the older ~1,500-line middle onto that path, not writing something new.

*Do it in slices, gate-green after each* — this is the one item where a big-bang change would be
hard to review. Suggested order: characterisation tests on current output first (the file has none,
so byte-identical output is the only safe contract), then migrate one card family at a time.
*Done when:* a new payments card can be added without writing a Python function, output is unchanged
through the migration, and the file has tests.

**B2. Pull SIBC ingestion into the manifest.**
The `atm_pos` manifest declares format/extract/validate/consolidate as gate stages. The `sibc`
manifest declares none of them — they are manual runbook steps, so the gate validates artifacts a
human produced through three unversioned commands.

Keep the date-normalisation A/B confirmation — it is a genuine judgment call (RBI's fortnightly
release must be remapped to a prior month-end). Make it an explicit human-gate *stage* rather than a
reason to live outside the gate.
*Done when:* both manifests declare the same ingestion shape, a SIBC period can be ingested through
`gate.py` alone, and the date confirmation still blocks on a human.

## Part 2 — Parked

Not being worked on. Recorded so it is not re-derived, and so the refactor above can be checked
against what it will eventually have to carry.

### P1. Twitter/X per-bank blurb feed

Machine emits a **blurb + a screenshot recipe**; the user screenshots and posts. Nothing automated
beyond the text.

**Constraint, already verified:** bank-level data is **payments-only** — 67 banks in `signals.db`,
all `atm_pos`. RBI SIBC is sector-level. Per-bank *credit* exists only in STRBI and only **annually**;
per-bank quarterly does not come from RBI at all. So this is a payments feed, permanently.

**Build it as a slot in the existing distribution layer, not a new system.** Reuse:
`core.traceability.DISTRIBUTION` + `validate_distribution` (numbers), `slot_render.lint_compliance`
(SEBI), `ledger.py` (the "not HDFC every week" mechanism), `signals/dominance.py` (attribution),
`_chart_recipe`/`FOCUS_CARD_TITLE` (screenshot recipe), and the established honest-null skip.

**Net-new compute: one thing** — a per-bank interestingness ranker, the bank-entity analogue of
`is_news.py`, built in the signal layer (the dashboard will want it too) and shipping with a
measured catch and false-rejection rate. Inputs already exist: the bank scans, the bank-divergence
signals, `csv_category_rotation`, the bank pair-gap.

Design leanings, to settle at build time: the unit of a post is a **divergence between two banks or
a bank vs its category**, not one bank's number in isolation · weekly at most, skipping freely ·
its own category in `categories.py` so it can't collide with the LinkedIn slots · every named-bank
claim passes through `dominance.py`, since a single-issuer artifact is *more* dangerous at bank
granularity than at aggregate.

### P2. New data sources

Inputs: `dbie_ingestion_context.md` + `rbi_reports_complete_v3.xlsx` (P-list: 22 sources, P0 done,
21 to go). Full reasoning in memory (`project_new_sources_roadmap`); the essentials:

- **DBIE is the portal, not a source.** It hosts most of the P-list. Build one pipeline per
  *dataset*; DBIE is a download route. A "DBIE pipeline" would be exactly the monolith
  `validate_composition` exists to prevent.
- **Three capabilities the architecture lacks.** (1) **Cadence** — `registry.json` has no frequency
  field, 0 of 230 signals; everything assumes monthly while the incoming sources are quarterly,
  annual, half-yearly, bi-monthly and fortnightly. This is the real blocker and is cheap to fix
  before a third source, expensive after. (2) **Granularity axes are fine** — `entity_type` is
  already free-text, so geography/state/rate-slab need no schema change, only ontology vocabulary
  discipline. (3) **No PDF extraction exists at all**, and **11 of the 21 remaining sources are
  PDF-only** — half the backlog behind a capability that is its own project, and one where
  traceability-by-construction is hardest.
- **Which source is #3 is unresolved and does not need resolving now.** The credit-side reading
  favours **Cluster B, price of credit** (smallest structured ingest that still proves the manifest
  generalises; forces exactly one new concept — cadence; turns "what is growing" into "starved by
  price or by volume"). The archived retail plan named **VAHAN/FADA** deliberately, as the test of
  whether the generic gate absorbs a non-RBI source. Both are defensible; they serve different
  audiences. Decide when source work actually starts.
- **Tracker correction outstanding:** P20 "Payment System Indicators" is marked *To do* although RBI
  ATM/POS card statistics are already ingested — related but distinct releases. Fix so the roadmap
  doesn't double-count.
- **Discipline to hold:** the raw data is free, so the data is not the moat — synthesis is. Every
  added source must earn a cross-source join (L2b) or a causal force (L2a), not just a new chart.

### P3. Engineering artifacts from the archived retail plan (EN-1, EN-2, EN-4)

Kept verbatim in intent because they were execution-ready decisions, not sketches. None is built.

- **EN-1 · Entity→ticker is a mapping artifact, never a model edit.** `analysis/ontology/ticker_map.json`,
  a peer of `concepts.json`/`channels.json`: URN → `{ticker, exchange, relationship,
  transmission_note}`, `relationship ∈ pure_play | major_segment | partial`, many-to-many expected.
  URNs may be entity **or** ecosystem-construct URNs (a construct is often the right transmission
  anchor and brings its evidence set with it — see `COMPOSITION_SPEC.md` §14). Plus
  `validate_ticker_map.py` wired into both gates. The stock↔signal table is **derived, not authored**:
  a script walks ticker_map → entity → registered signals → compact
  `web/public/data/stock_signal_map.json`; the web app reads only that artifact. This keeps one
  generic mechanism — any future pipeline's entities become investable coverage by adding rows.
- **EN-2 · Where things live.** Same repo (a separate one would fork the single source of truth;
  revisit at rebrand as a *rename*, never a split) · **call register** = append-only
  `analysis/call_register.json` (`id, date, claim, basis(signal_ids), review_date, status, resolution`),
  permanent IDs like annotation IDs, public `/register` route, and its own Check-2g-style validator
  once the first calls are logged · **release calendar** = `analysis/release_calendar.json`
  (`source, cadence, expected_day, publication_lag, url`) — a data artifact, drafted by the model,
  **dates signed off by the user**, same A/B gate pattern as `detect_format.py` · web app v0 lives
  in the existing Next.js app reusing AppShell + DLS; email magic-link **reactivates the dormant
  Clerk integration**, never a new auth system · the SEBI lint hardens **before** the first note ships.
- **EN-4 · VAHAN/FADA as a pipeline** follows the atm_pos template exactly:
  `analysis/pipelines/vahan/` + a manifest, Stage 0 detect-format → extract → validate → consolidate
  → L1 specs in `registry.json` + a compute module. No one-off scripts. If the generic gate can't
  absorb it cleanly, **that is a finding to fix in `core/`, not to work around per-pipeline.**
