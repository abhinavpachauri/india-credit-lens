# Platform Review — 2026-08-11

Full-folder analysis pass. **No code was changed.** Three lenses: build pipelines, tech
architecture, design system. Findings are ranked at the end.

Scope: 82 live Python modules (~39k LOC incl. legacy), 8.2k LOC of web TS/TSX, 269 Python
tests + 19 vitest, 2 pipelines, 3 routes, 230 registered signals.

**Headline:** the architecture largely holds. The manifest gate, the shared traceability
policy, the signal store and the read-mode shell are all genuinely generic and would survive
a third pipeline. Three things have drifted, all in the same direction — **the payments
pipeline carries a large hand-written insight layer that the credit pipeline does not**, the
**ingestion halves of the two pipelines are asymmetric** (one in-gate, one manual), and the
**design system stops at colour** while typography, spacing and the third route went their
own way. Plus a meaningful amount of dead surface accumulated in `web/`.

---

## 1. Build pipelines — ingestion, generation, gates, verification

### What holds

**The manifest gate is the real thing.** `analysis/core/gate.py` (356 LOC) contains no
pipeline-specific logic whatsoever — it resolves logical stage names through `CORE_MAP`, reads
an ordered stage list from `pipelines/{id}/pipeline.json`, and executes. Adding pipeline #3
means writing one manifest and its per-pipeline modules; the runner does not change. This is
the §4 cutover paying off exactly as designed.

**Verification is layered and mostly deterministic**, and the layering is coherent:

| Layer | Guard | Ground truth |
|---|---|---|
| Raw data | Stage 0 format detect, Stage 1/2 schema + integrity | the XLSX itself |
| Stored signals | Check 2e (integrity), **2f (freshness)** | recompute every period from CSV, diff |
| L1 insight numbers | Check 2g (SIBC), Stage 4c (payments) | `signals.db` |
| L2 opportunity numbers | Check 4f, strict both pipelines | driver's `evidence_all` |
| Published prose | `validate_distribution.check_doc` | per-block declared scope |
| Docs | `architecture/reconcile.py --strict` | code + disk |

Check 2f is the strongest piece in the codebase: it doesn't trust the DB, it recomputes all
2,535 SIBC rows from the CSV and fails on any drift. That is the pattern the rest of the
platform should be judged against, and mostly is.

**Gates were run as part of this review** — SIBC merged gate: ALL STAGES PASSED, 269 tests,
`tsc` + `npm run build` green, reconcile clean.

### What has drifted

**1a. Ingestion is in-gate for payments, manual for credit.** The `atm_pos` manifest declares
`format → extract → validate_data → consolidate` as gate stages. The `sibc` manifest declares
none of them — `detect_format.py`, `extract_sibc.py` and `update_web_data.py` are run by hand
from the runbook before the gate starts. So for SIBC, the gate validates artifacts that a
human produced through three unversioned steps; for payments it produces them itself. Two
ingestion contracts for two pipelines is precisely what the manifest was built to prevent,
and it will be re-litigated with source #3.

Part of this is *justified* and should be kept: the SIBC date-normalisation A/B confirmation
is a genuine human judgment call (RBI publishes a fortnightly release that must be remapped
to a prior month-end, and new raw dates need classifying). But "a human confirms the remap"
does not require "the extract step lives outside the manifest" — the stage could run in-gate
and block on confirmation.

**1b. Two intermediate representations for the same job.** SIBC insights read from
`signals.db` directly. Payments insights read from `analysis/rbi_atm_pos/signals.json`, a
602-LOC payload rebuild (`compute_atm_pos_signals.py`, Stage 4a) that exists only for this
pipeline, and which Stage 4c then has to *drift-guard against `signals.db`* because it is a
second copy of numbers the DB already holds. That drift guard is good engineering on top of a
structure that shouldn't need it.

**1c. The freshness guard has two holes.** `guards/check_derived_fresh.py::DERIVED_GLOBS`
lists 14 derived artifacts but omits the two largest ones the gate itself writes:
`web/public/data/sibc_l1_annotations.json` (130 KB, written by Stage 5.5) and
`web/public/data/atm_pos_insights.json` (95 KB, Stage 4b). Also missing:
`atm_pos_signals.json`. These are committed derived files with no staleness guard — the exact
failure class that caused the "FY26 acceleration jumped to 7.1pp" incident.

**1d. LLM stages are outside the gate** (`append` / `evaluate` are manual runbook steps). This
is deliberate and correct — they cost money and shouldn't run on every gate invocation — but
it means the gate can pass against an evaluation from a previous period. Worth an explicit
in-gate assertion that the newest eval period matches the newest signal period, rather than
relying on runbook order.

### Verdict

Ingestion and verification are strong where they are generic and weak exactly where they are
per-pipeline. Nothing here is broken; two of the four items (1a, 1b) are the same finding as
§2 below seen from the data side.

## 2. Tech architecture — does the refactor still hold?

### What holds, concretely

- **`core/` is genuinely shared.** `core.paths` is imported by 48 modules; `core.traceability`
  by 12 including **both** traceability validators — so the number-extraction and matching
  *policy* is one implementation with per-surface tunings (`SIBC`, `ATM_POS`, `DISTRIBUTION`),
  not three parallel regex sets. `core.voice` (5 consumers) and `core.render.fmt_value` (9
  consumers) did the same for prose and formatting. This is the strongest evidence the
  "build once, reuse" principle is real rather than aspirational.
- **The relational-signal layer is one mechanism on both trees.** `core/relational_insights.py`
  serves rotation and divergence for both pipelines; both insight generators call it.
- **The read-mode UI is the model case.** 397 shared LOC (`ReadModeShell` + `parts`) against
  128 + 102 LOC of thin per-pipeline adapters. The pipeline supplies a data model and a chart
  renderer; nothing else. This is what §1a and §2a should look like.
- **Test coverage grew from 9 tests to 269** and covers the deterministic compute core
  properly (13 test files touch `compute/sibc`, 7 touch `compute/atm_pos`).

### 2a. The single biggest violation: the payments insight generator

`pipelines/atm_pos/generate_atm_pos_insights.py` is **2,086 lines** — the largest live module
in the repo — and it is built as **~30 hand-written functions, one per dashboard card**:
`cc_ecom_vs_pos`, `dc_atm_trend`, `infra_qr_per_pos`, `gap_bharat_qr_contraction`, and so on,
collected into a `RULES` list.

The SIBC equivalent, `pipelines/sibc/generate_analysis_report.py`, is **502 lines** and is
*registry-driven*: it iterates the evaluation's signals generically, routes them to UI
sections through a map, and renders scans deterministically. Adding a SIBC card means adding
a registry entry. **Adding a payments card means writing a new Python function.**

This is the "one generic mechanism per pipeline, not per-pipeline one-offs" rule inverted, and
it is the single thing in the codebase that would not survive source #3 — a third pipeline
built this way adds another 2,000 lines. It is also **the largest untested module in the
repo**: no test file exercises it directly.

Mitigating: the newer parts of the file (the `EVAL_ANCHOR` LLM-representation layer,
`relational_cards`, `pair_cards`, `_dominance_caveat`) *are* generic and shared with SIBC. The
one-off layer is the older ~1,500-line middle of the file. So the fix is a migration, not a
rewrite — the generic path already exists alongside it.

### 2b. Duplicated helpers in the compute layer

`signals/compute/sibc.py` and `signals/compute/atm_pos.py` each carry private copies of the
same helpers. Measured similarity:

| Helper | Similarity | Note |
|---|---|---|
| `_eval_status` | **100%** | byte-identical status-rule evaluator |
| `_rotation_rows` | **98%** | the shared Δshare algorithm, copy-pasted |
| `_prior_year` | 88% | |
| `_prior_period`, `_unknown`, `_month_back`, `_row` | 65–72% | drifted copies of one idea |

`_eval_status` and `_rotation_rows` belong in `signals/compute/common.py`. They agree today
and could drift tomorrow — the exact "parallel copies that agree today" the root CLAUDE.md
forbids.

**Sharper sub-finding:** `csv_streak` exists in both modules with **14% similarity**. One
registry method name resolves to two materially different implementations depending on
pipeline. A registry spec that means different things per pipeline is a latent correctness
bug, not just a reuse miss — it should either be two named methods or one shared one.

### 2c. Registry status field is carrying a false value

34 SIBC Layer-2 signals have `retire_period` and `migrated_to` set, but their
`current_status` is **`pending`** — the string `"retired"` appears **zero times** in
`registry.json`, even though `validate_signal_history.VALID_STATUSES` accepts it and the
session record says they were retired. Consequence: the registry reports 38 "pending" signals
when only 4 are genuinely awaiting compute; any status-driven consumer treats 34 retired
trackers as live-but-uncomputed. Cheap fix, real integrity smell.

### 2d. Evidence pointers in JSON are unguarded

`reconcile.py` validates script and artifact paths named in the **markdown** docs — and it
works (it caught the mermaid-generator deletion). But it doesn't scan JSON. So
`distribution/ai_pm_register.json` still cites `analysis/newsletter/validate_newsletter.py` as
the **source file for two published measurements** — a path deleted on 2026-07-21 when the
newsletter folded into distribution. The register's own admission rule is "no publish without
a value *and* a source file". Extending reconcile's artifact check to declared-source fields
in JSON closes this and is a small change.

### 2e. Naming and layout debt

- **`analysis/cross_source/` (data) and `analysis/crosssource/` (code)** are two directories
  differing by one underscore. This is a genuine trip hazard when reading or writing paths.
- 460 KB / 11 modules in `legacy/`, correctly quarantined, but `legacy/newsletter_v1/` alone
  is 3,377 LOC that no longer has a decision pending on it.
- `rebuild_sibc_signals.py` + `rebuild_atm_pos_signals.py` (1,137 LOC combined) are flagged by
  reconcile as mentioned in no living doc — likely superseded by `generate_signal_history
  append`, but currently in neither the live set nor `legacy/`.
- `trading_system.db` sits at repo root and belongs to no pipeline in this project.
- 12 markdown files at repo root, 5 of them `HANDOFF_*` snapshots of finished work. The
  living-vs-historical split is understood by `reconcile.py` but not by a human opening the
  folder.

### 2f. Test coverage gaps, ranked by risk

| Module | LOC | Direct tests | Risk |
|---|---|---|---|
| `pipelines/atm_pos/generate_atm_pos_insights.py` | 2,086 | **0** | highest — most logic, least generic |
| `core/generate_skeleton.py` | 579 | **0** | deterministic, regenerated every gate run |
| `core/derive_opportunities.py` | 191 | **0** | drives every opportunity's status |

`generate_skeleton` is the cheapest win: it is pure and deterministic, it runs in both gates,
and a golden-file test would cost very little.

### Verdict

The refactor holds. `core/` is real, the manifest is real, the read-mode shell proves the
pattern generalises to the UI. The debt is concentrated in one module (2a) plus a handful of
small hygiene items. Nothing here argues for another restructure.

## 3. Design consistency and the design system

### What holds

- `AppShell` owns dark mode and renders `Header` exactly once; both dashboards comply.
- Colour is properly tokenised: `lib/theme.ts` + CSS custom properties, used across 34
  component files. Dark mode works through variables rather than per-component branching.
- The DLS components (`InsightCard`, `InsightCTAStrip`, `OpportunityTeaser`) are shared by
  SIBC and payments, and `SectionCard` is one shell for both.
- Read mode is consistent across pipelines by construction (§2 above), which is the newest
  and best-factored part of the front end.

### 3a. `/opportunities` is outside the design system entirely

The third route is **468 LOC of bespoke UI**. It imports no DLS component. It hand-rolls
`OppCard`, `StatusPill`, `FlipZone`, `BasisBlock` and `ChartPanel` — re-implementing concepts
the DLS already owns (left-accent card, expandable inference chain, "For lenders" implication
block, controls card). It doesn't call `useAppShell`. It carries 8 hardcoded hex values.

It is the only page a paying visitor would see as the "premium" surface, and it is the least
systematic one. This is the clearest design-consistency finding in the repo.

Note this interacts with an open product decision: read mode already renders Deep
(opportunities) **inline**, and the spec says `/opportunities` is retired only after reviewing
that fold. So the right move may be deleting this page rather than restyling it — worth
deciding before investing in it either way.

### 3b. The design system stops at colour

There is no type scale, spacing scale or radius scale. Measured across `app/` + `components/`:

- **7 distinct border radii** in use: 4, 6, 8, 10, 12, 20 px.
- **12+ ad-hoc font sizes**, including 12.5, 13.5 and 14.5 px — values that only appear
  because a component was nudged by eye.

The read-mode build introduced its own `STYLE` object in `components/read/parts.tsx`, which is
in practice a small, coherent token set — it is the natural thing to promote into `lib/theme.ts`
(or a sibling `tokens.ts`) and adopt elsewhere, rather than authoring a scale from scratch.

### 3c. Colour tokens live in two homes

`SEC_COLORS` (SIBC sections) is in `lib/theme.ts`; `GROUP_ACCENT` (payments groups) is in
`lib/atm_pos_data.ts` — a *data* module. Same role, two locations, and a pipeline's accent
palette is now coupled to its data loader.

### 3d. Explore mode is two implementations — deliberately

`SectionWithAnnotations` (232 LOC) vs `AtmPosGroupSection` (427 LOC), plus `TrendChart`/
`AtmPosTrendChart` and `DistributionChart`/`AtmPosDistributionChart` as parallel pairs. This
was **decided** on 2026-07-21 with an explicit revisit trigger ("several more pipelines
ingested"), so it is a recorded trade-off, not drift. Recording it here so it isn't
re-discovered as a bug — but note the trigger and the §2a trigger are the same event, and
both point at the same next pipeline.

### 3e. Dead surface in `web/`

**Nine components have zero importers**, and two more are imported only by dead ones:

```
AnnotationControls  AnnotationPanel  AtmPosFilterBar  EmailGate  NewsletterCTA
StoryFilterBar      SystemView       SystemViewText   TabBar
CytoscapeGraph, SubstackCTA  (imported only by SystemView)
lib/system_model_data.ts     (feeds only the above)
```

**1,813 LOC dead**, and it carries three npm dependencies (`cytoscape`, `cytoscape-dagre`,
`@types/cytoscape`) into the bundle graph for a feature no route renders. `NewsletterCTA` is
newly dead by today's deliberate decision and should stay; the rest is accumulation.

`SystemView` + `CytoscapeGraph` is a whole causal-graph visualisation feature that is
unrouted. Worth an explicit decision: revive it (the v4.0 system model would now feed it far
better data than when it was written) or retire it to keep the folder honest.

### 3f. A 4.9 MB file is deployed and never requested

`web/public/data/atm_pos_consolidated.csv` is **84% of the entire `public/data` directory**
(4.9 MB of 5.8 MB), is git-tracked, and is fetched by **nothing** — `lib/atm_pos_data.ts`
switched to the 353 KB precomputed `atm_pos_chart_series.json` in the compute-once-ship-compact
pass, but the raw CSV was never removed. It costs no page weight (nothing requests it) but it
ships to the CDN on every deploy and bloats the repo.

Either it is intentionally a public data download — in which case it should be documented and
linked — or it is residue from the perf fix. Meanwhile SIBC still fetches its raw CSV
(`lib/data.ts:26`), which is the acknowledged two-mechanism drift; at 179 KB it is not urgent,
but it is the same inconsistency.

## Documentation drift found in passing

`reconcile.py` guards *paths*, not *claims*, so numeric and status claims have rotted:

- `CLAUDE.md:63` says the registry holds **225 signals**; `CLAUDE.md:192` says **90**; the
  actual count is **230**. Two contradictory numbers in one file.
- `CLAUDE.md` still lists "authoritative `ARCHITECTURE.md`" as a **gap** in the engineering-health
  track. It was written — `ARCHITECTURE.md` + the generated `ARCHITECTURE.generated.md`
  (freshness-guarded) both exist. The backlog item is done and should be struck.
- `CLAUDE.md` lists "unit tests for the deterministic core (today: 1 file/9 tests)" as the
  highest-ROI gap. Now 17 files / 269 tests. Still true for the three modules in §2f, but the
  headline number is badly stale.

A cheap extension to `reconcile.py`: assert that counts stated in living docs match the
artifacts they describe (registry signal count, test count, period count). Same pattern as the
path check, same payoff.
